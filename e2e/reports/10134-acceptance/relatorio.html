CA01 — Conjuntos idênticos ATENDIDO · automatizado

Critério (Gherkin): Dado os arquivos `admin/src/style.css` e `client/src/style.css` Quando extraio a lista de custom properties declaradas em cada um Então os conjuntos de nomes são idênticos (diff vazio) E `--color-success`, `--color-success-foreground`, `--color-warning` e `--color-warning-foreground` existem nos dois

Como foi testado: Rodado scripts/check-design-tokens-parity.mjs contra o conteúdo real dos commits mesclados (git show origin/develop:src/style.css de cada submódulo, extraído para arquivos temporários — os checkouts locais reais de admin/ e client/ não foram tocados). O script extrai os nomes de custom property dos três blocos (:root, .dark, @theme inline) e compara os conjuntos.

Resultado observado:
  • Saída completa em <code>parity-check-pos-merge.txt</code>: 67 tokens em <code>:root</code>, 55 em <code>.dark</code>, 74 em <code>@theme inline</code> — contagens idênticas nos dois arquivos.
  • <code>OK: paridade de nomes de token confirmada nos três blocos</code> — zero divergências, exit code 0.
  • Confirmado especificamente que <code>--color-success</code>, <code>--color-success-foreground</code>, <code>--color-warning</code> e <code>--color-warning-foreground</code> estão presentes no conjunto de 74 nomes de <code>@theme inline</code> de ambos os arquivos (antes do fix, só existiam no client — 10 divergências reais detectadas na varredura pré-fix, ver seção CA04 para o mecanismo de detecção).

CA02 — Paridade no modo escuro ATENDIDO · automatizado

Como foi testado: Mesma execução do CA01 — o bloco .dark é um dos três blocos comparados pelo script (não é uma checagem separada).

Resultado observado:

CA03 — Contraste AA nos tokens novos ATENDIDO · automatizado

Critério (Gherkin): Dado um alerta de sucesso e um de aviso renderizados no Admin Quando meço o contraste texto/fundo em claro e escuro Então a razão é ≥ 4,5:1 nos quatro cenários

Como foi testado: Cálculo real de contraste WCAG (conversão OKLCH→sRGB linear→luminância relativa→razão de contraste, fórmulas da especificação CSS Color 4 — sem biblioteca externa, script contrast-final.mjs ad-hoc) para os 4 cenários pedidos, usando os valores oklch efetivamente implementados (o .dark espelha exatamente o :root, então os cenários claro/escuro usam os mesmos números — validação intencional de que a decisão de não inventar tom novo para o modo escuro não compromete o contraste).

Resultado observado:
  • success, tema claro: 6.99:1 (≥4,5:1)
  • success, tema escuro: 6.99:1 (≥4,5:1) — mesmo valor do claro, porque o `.dark` espelha o `:root` (decisão registrada no overview da feature)
  • warning, tema claro: 7.38:1 (≥4,5:1)
  • warning, tema escuro: 7.38:1 (≥4,5:1)
  • Os 4 cenários passam com folga — não foi necessário ajustar nenhum valor de cor além dos já existentes no arquivo (RN da story: não alterar valores).

CA04 — Regressão bloqueada (caminho de erro) ATENDIDO · automatizado

Critério (Gherkin): Dado um PR que adiciona um token em apenas um dos frontends Quando o CI executa a checagem de paridade Então o job falha e a saída nomeia o token ausente e o frontend em que falta

Como foi testado: Demonstração do caminho de erro: criada uma cópia temporária do admin/src/style.css (pós-merge) com um token de teste injetado só nesse lado (--color-demo-only-admin-10134: #123456;, dentro do bloco @theme inline). Rodado o script de paridade contra essa cópia + o client/src/style.css real. Cópia temporária removida em seguida — nada do arquivo de demonstração foi commitado.

Resultado observado:
  • Saída (<code>ca04-deteccao-demo.txt</code>): <code>FALHA: 1 divergência(s) de paridade de token</code>, listando exatamente <code>@theme inline: --color-demo-only-admin-10134 ausente em client (presente em admin)</code> — nomeia o token e o frontend, conforme pedido.
  • Exit code real do processo Node: 1 (confirmado separadamente, sem o `tee` mascarar o código de saída) — o gate é efetivamente bloqueante, não apenas informativo.
  • Nota operacional registrada na revisão de código e no commit do workflow: como `admin/` e `client/` são repositórios com CI próprio e o meta-repo historicamente recebe bumps por commit direto (não por PR), o gate roda no meta-repo (único ponto com os dois submódulos simultaneamente) mas não bloqueia a PR de origem antes do merge — decisão consciente do usuário, documentada no commit `feat(ci): adiciona gate de paridade...`.
