Resumo

4 critérios de aceite, todos de mecanismo de CI/tooling (sem UI navegável) — evidenciados via execução direta dos scripts scripts/check-color-tokens.mjs em admin/ e client/, já mergeados em develop. CA01: varredura da baseline sem violação fora da allowlist nos dois frontends. CA02: cada entrada da allowlist tem caminho e justificativa não-vazia. CA03: injeção de #ff0000 fora da allowlist faz o script falhar (exit 1) apontando arquivo:linha, nos dois frontends. CA04: adicionar uma entrada justificada à allowlist faz o script voltar a passar (exit 0), com o diff da allowlist visível — provado e revertido nos dois frontends. Resultado geral: 4/4 atendidos.

CA01 — Varredura limpa na linha de base ATENDIDO · automatizado

Critério (Gherkin): Dado o código atual de admin/src e client/src Quando executo a checagem de cor literal (#rrggbb, rgb(), rgba(), hsl()) Então nenhum arquivo .vue acusa ocorrência fora da allowlist.

Como foi testado: Executado npm run check:colors (que roda node scripts/check-color-tokens.mjs) na raiz de admin/ e de client/, ambos no estado atual de develop pós-merge dos PRs #72 e #62.

Resultado observado:
  • admin/src: 586 arquivos .vue varridos, resultado 'ZERO cor literal fora da allowlist' (exit 0).
  • client/src: 298 arquivos .vue varridos (inclui src/components/ui/**), resultado 'OK: zero cor literal fora do token' (exit 0).

Evidência por cobertura automatizada — ver Anexo.

CA02 — Allowlist explícita e justificada ATENDIDO · automatizado

Critério (Gherkin): Dado o arquivo de configuração da guarda Quando o inspeciono Então cada entrada da allowlist tem caminho e uma linha de justificativa.

Como foi testado: Inspecionado o array ALLOWLIST declarado em scripts/check-color-tokens.mjs de cada frontend.

Resultado observado:
  • admin: 2 entradas (MapPointPicker.vue, GeoLayerPreviewMap.vue), cada uma com campo file e reason não-vazio.
  • client: 1 entrada (MapPointPicker.vue), com campo file e reason não-vazio.
  • Ambos os scripts recusam rodar (erro de configuração distinto de violação) se qualquer entrada tiver reason vazio — validado no código de validateAllowlist().

Evidência por cobertura automatizada — ver Anexo.

CA03 — Violação barra o PR (caminho de erro) ATENDIDO · automatizado

Critério (Gherkin): Dado um PR que introduz #ff0000 em um .vue Quando o CI executa Então falha e a saída aponta arquivo:linha da ocorrência.

Como foi testado: Criado um arquivo temporário src/components/__proof10135__.vue com color: #ff0000 fora da allowlist, em admin/ e em client/; rodado npm run check:colors em cada um; arquivo removido ao final.

Resultado observado:
  • admin: script falha (exit 1), aponta 'src/components/__proof10135__.vue:2 — #ff0000'.
  • client: script falha (exit 1), aponta 'src/components/__proof10135__.vue:2 #ff0000'.
  • Em ambos, a mensagem final orienta corrigir com token semântico ou allowlistar com justificativa.

Evidência por cobertura automatizada — ver Anexo.

CA04 — Exceção nova é possível sem contornar a guarda ATENDIDO · automatizado

Critério (Gherkin): Dado um caso legítimo novo (lib imperativa que exige cor concreta) Quando adiciono o arquivo à allowlist com justificativa Então o CI volta a passar, e o diff da allowlist fica visível na revisão.

Como foi testado: A partir do estado de violação do CA03, adicionada uma entrada { file: 'src/components/__proof10135__.vue', reason: '...' } à ALLOWLIST de cada script (via git diff, mudança visível); rodado npm run check:colors novamente; allowlist e arquivo de prova revertidos ao final.

Resultado observado:
  • admin: com a entrada adicionada, script volta a passar (exit 0), lista a nova exceção com sua justificativa entre as 'Exceções ativas'.
  • client: mesmo resultado — exit 0, nova exceção listada entre 'Excecoes declaradas'.
  • O diff da allowlist (git diff) é a evidência de que a mudança fica visível na revisão do PR — nenhum mecanismo de silenciamento fora da allowlist foi usado.

Evidência por cobertura automatizada — ver Anexo.
