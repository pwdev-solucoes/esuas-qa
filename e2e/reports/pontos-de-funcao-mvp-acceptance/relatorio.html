Metodologia (CA02/CA03 — como reproduzir esta contagem)

Método: IFPUG detalhado (ALI/AIE por função de dados; EE/SE/CE por função transacional), complexidade pelas tabelas padrão do CPM, PF não ajustados (VAF e as 14 características gerais do sistema ficam fora de escopo — decisão da US-09).

Convenção de DET (Tipo de Dado / Data Element Type): para funções de dados, DET = número de colunas de dado da tabela na migration mais recente, excluindo id, uuid, created_at, updated_at, deleted_at (campos técnicos, não reconhecíveis pelo usuário). Para funções transacionais, DET ≈ número de campos de entrada + saída distintos cruzando a fronteira (aproximado a partir das colunas envolvidas + confirmação/id retornado), sem contar duas vezes o mesmo campo.

Convenção de RET (Tipo de Registro / Record Element Type): RET=1 para toda tabela simples de lookup. RET>1 quando a tabela tem subgrupos de dados claramente distintos (ex.: families tem registro/renda/contato/vulnerabilidade como blocos separados). Uma tabela filha com CRUD próprio e independente (rota dedicada) é contada como ALI separada, não como RET da tabela pai — ex.: tenant_responsibles é ALI própria, mas geo_layer_tenants (pivot sem CRUD próprio) é RET de geo_layers.

Convenção de FTR (Arquivo Referenciado / File Type Referenced): FTR = 1 (a própria ALI mantida) + 1 para cada outra ALI/AIE já contada nesta lista que a transação valida ou lê (chave estrangeira obrigatória, junção de exibição). Referências a campos de auditoria (created_by/updated_by) não somam FTR.

Entidades compartilhadas contadas uma única vez: addresses (endereço genérico, usado por social-units, tenants, families etc.) é contada como 1 AIE só na primeira aparição (módulo tenants), e só referenciada por FTR nos módulos seguintes — nunca duplicada. Módulos client que reusam o mesmo backend do admin (legal-acceptance, tenant-settings, users, platform-updates) reusam a(s) ALI(s) já contada(s) no admin — só as transações de auto-serviço do client são novas.

Convenção de agregação (só para reduzir repetição de linhas idênticas): quando um módulo tem o conjunto padrão de transações de manutenção (store/update/destroy/bulk-activate/ bulk-deactivate) com FTR e DET idênticos entre si, elas aparecem em uma linha agregada citando os nomes das ações — cada uma continua sendo uma função transacional distinta pela definição IFPUG, só a apresentação é agrupada. A evidência (caminho do arquivo de rotas) é a mesma citada.

Caso contrário é CE (mera listagem/consulta).
